# 提示词技术分类体系

> 分类原则：**按认知机制分层，而不是按技术名词罗列。**
> 判断标准只有一个——这条提示词，究竟改变了模型的哪一个环节。

---

## 为什么要这样分

常见的"20 种提示词技巧"清单是名词表，不是分类：CoT、Few-shot、ReAct 被平铺并列，看不出它们解决的是同一个问题还是三个问题。结果是**学到一堆招式，不知道什么时候该出哪一招**。

按认知机制分层后，六个类别对应六个不同的失效原因。诊断问题时先定位类别，再选技术，路径才收敛。

---

## 六类总览

| 类 | 改变的环节 | 解决的核心问题 | 典型失效症状 |
|---|---|---|---|
| **A 语境注入** | 输入信息 | 模型不知道 | 答非所问、缺少领域背景、风格不对 |
| **B 推理激发** | 计算步数 | 模型没算够 | 复杂推理跳步、数学错、逻辑断链 |
| **C 结构约束** | 输出分布 | 模型没说清 | 格式漂移、JSON 不合法、长度失控 |
| **D 流程编排** | 任务拓扑 | 任务太复杂 | 长任务中途跑偏、一步做不完 |
| **E 反馈迭代** | 输出质量 | 第一版不够好 | 表面合理但细节错误、语气不稳 |
| **F 元层自动化** | 提示词本身 | 手写调不过来 | 人工试错成本高、跨模型不可迁移 |

前四类是**往模型里加东西**，后两类是**让模型管自己**。

---

## A 语境注入（Context Injection）

**机制**：模型输出是 `P(输出 | 提示词, 参数)`。这一类不改变推理方式，只改变条件分布的输入侧——把模型缺的信息补上。

**技术清单**

| 技术 | 做法 | 适用 |
|---|---|---|
| Zero-shot | 直接给指令，不给例子 | 简单、定义清晰、模型已"会"的任务 |
| Few-shot | 给 1–5 组「输入 → 期望输出」配对 | 格式对齐、风格克隆、分类标注体系 |
| 背景/上下文注入 | 提供领域知识、文档片段、用户画像 | 垂直领域问答、企业知识库 |
| 角色 / 人格设定 | 指定身份、资历、听众、口吻 | 需要统一语气或多轮一致性的场景 |
| RAG 接地 | 检索片段拼入上下文 + 限定只用检索内容作答 | 事实性问答、需要引用溯源 |

**关键判断（2026 现状）**
Few-shot 的收益点已经从"教能力"迁移到**"教格式与教风格"**。强模型 zero-shot 就能做分类，但对齐一个特定表格结构、特定键名、特定文风时，3 个例子依然最快最稳。

**失效边界**
- 例子数量超过 5 个后边际收益骤降，且挤占上下文
- 例子本身有错或有偏，会被原样放大
- 示例分布与真实输入分布不一致 → 负迁移

---

## B 推理激发（Reasoning Elicitation）

**机制**：把单次前向传播的"直觉作答"拆解成多步显式推理，用更多 token 换更高准确率。

**技术清单**

| 技术 | 做法 | 适用 |
|---|---|---|
| CoT | 要求先展示推理过程再给结论 | 数学、逻辑、多步推导 |
| Zero-shot CoT | 仅加"让我们一步步思考" | 无示例可用时的快速提点 |
| Self-Consistency | 采样多条推理路径，取多数答案 | 高 stakes 推理、允许更高成本 |
| ToT / GoT | 显式展开多条分支，评估后回溯 | 规划、搜索类问题 |
| PoT / PAL | 让模型生成程序，由解释器执行 | 精确计算、数值任务 |
| Reflexion | 推理 → 失败 → 反思记录 → 重试 | 多轮尝试型任务 |

**关键判断（最重要的一条）**
凡是带**显式推理档位**的模型（GPT 系的 reasoning effort、Claude 的 extended thinking、Gemini 的 thinking / Deep Think、DeepSeek-R1、Qwen3 与 GLM 的 thinking 模式），内部已有训练好的推理轨迹。此时：

- 再写"请一步步思考"是**冗余甚至有害**——与内置轨迹冲突，表现为过度冗长或提前收敛
- 正确用法是**调档位参数 + 给判定标准**，而不是手写 CoT
- 手写 CoT 只在**非推理档位**（标准模式、小模型、本地部署的小参数模型）上仍然有效

**失效边界**
- 简单任务上开 CoT 只会增加延迟与 token 成本，不提升准确率
- CoT 提升的是"推理透明度"，不等于"推理正确性"——模型可以一步步地推出错误答案
- Self-Consistency 成本是单次的 N 倍，且需要可判定的聚合规则

---

## C 结构约束（Structural Constraint）

**机制**：不追求模型"更聪明"，而是收窄合法输出空间。

**技术清单**

| 技术 | 做法 | 层级 |
|---|---|---|
| 格式模板 | 在 prompt 中给出输出骨架 | 软约束 |
| JSON Schema / 结构化输出 | 通过 API 传入 schema | **硬保证** |
| 约束解码 | 在解码层限制合法 token | **硬保证** |
| 负向约束 | 明确禁止项（长度、禁用词、禁幻觉） | 软约束 |
| 护栏与边界 | 定义拒答条件、降级行为 | 软约束 |

**关键判断**
生产环境中需要机器解析的输出，**必须走 API 原生 schema / constrained decoding**，而不是在 prompt 里恳求模型。Prompt 只能提高概率，schema 是硬保证——这是专业与业余的分水岭。

**另一条独立体系**：图像生成模型的**负向提示词（Negative Prompt）**与 LLM 提示词几乎无共通之处，需单独成体系处理（见 `05-templates/`，待建）。

**失效边界**
- 约束条目超过约 7 条后，模型开始选择性忽略，需改为分层或程序化校验
- 否定句（"不要做 X"）在部分模型上反而激活 X，应改写为正面指令

## D 流程编排（Orchestration）

**机制**：把一个超出单次上下文承载力的任务，拆成多个可控子任务并串联。

**技术清单**

| 技术 | 做法 | 适用 |
|---|---|---|
| 任务分解 | 显式拆子目标，逐个求解 | 长文档、多步骤创作 |
| Prompt Chaining | 上一步输出作为下一步输入 | 提取 → 分析 → 生成 类流水线 |
| 路由分发 | 先分类，再走对应子提示词 | 多意图混合输入 |
| ReAct | 思考 → 行动 → 观察 → 再决策 | 需要调用外部工具的动态任务 |
| 工具调用 | 声明可用函数，由模型决定调用 | API 集成、数据查询 |

**关键判断**
判断是否需要编排的标准：**单条 prompt 的失败是否可定位**。如果错了不知道错在哪一步，就该拆。

**失效边界**
- 链式调用会累积误差，环节越多整体成功率衰减越快（单步 95% × 5 步 ≈ 77%）
- 中间步骤必须设定可校验的交付物，否则错误会无声传递
- 过度拆分会让总成本与延迟失控

---

## E 反馈迭代（Feedback Loop）

**机制**：让模型对自身输出施加批判与修正，模拟人类"写完改一遍"的过程。

**技术清单**

| 技术 | 做法 |
|---|---|
| Self-Refine | 生成 → 自评 → 重写 |
| Critique-Revise | 由独立角色执行批评，另一角色执行修改 |
| Constitutional | 用一组明文原则约束模型自我修正方向 |
| 多轮验证 | 用确定性规则（正则、schema 校验、代码执行）做硬校验后回喂 |

**关键判断**
迭代的前提是**存在可判定的评分标准**。没有判据的"请再优化一下"是在让模型随机游走，常见结果是长度增加但质量不变。

把批评者角色与生成者角色分开，效果显著优于让同一模型自评自改——自评会放大原有偏见。

**失效边界**
- 迭代 2–3 轮后收益饱和，继续迭代易出现"改坏"（过度迎合批评意见）
- 模型对批评意见的接受度过高，可能把正确的部分改掉，需保留上一版做对比

---

## F 元层自动化（Meta-level Automation）

**机制**：把提示词本身当作可优化对象，用模型或搜索算法生成与迭代提示词。

**技术清单**

| 技术 | 做法 | 适用 |
|---|---|---|
| Meta-Prompting | 让模型为某任务设计提示词 | 冷启动、不确定如何表述 |
| APE | 候选提示词自动生成 + 在验证集上打分择优 | 任务量大、有验证集 |
| DSPy 式编译 | 把 prompt 当参数，用优化器自动搜索 | 工程化、持续迭代的系统 |
| 版本化与评测 | prompt 进版本控制，绑定回归测试集 | **所有生产场景** |

**关键判断**
元层的价值不在"自动写出更好的 prompt"，而在**把提示词从 artifact 变成 asset**——可版本化、可回归、可 A/B。这一条是规模化落地的前提。

**推荐分工**：强模型生成提示词 → 弱模型/便宜模型执行 → 用独立判据评分。不要让同一模型既写又评。

**失效边界**
- 自动优化需要验证集，没有验证集就只能靠人工评测，成本反而更高
- 优化出的提示词常过拟合到验证集，需在留出集上复核
- 优化结果可解释性差，出问题难以定位

---

## 组合使用模式

单类技术很少单独奏效。常见且经过验证的组合：

| 场景 | 组合 | 说明 |
|---|---|---|
| 企业知识库问答 | A(RAG) + C(引用格式) + C(拒答规则) | 接地 + 溯源 + 无据可依时明确说不知道 |
| 长文档分析 | D(分解) + B(推理档位) + C(输出 schema) | 先拆后算，结果结构化 |
| 批量数据抽取 | A(Few-shot) + C(原生 schema) + E(硬校验回喂) | 例子定格式，schema 保合法，校验兜错 |
| 创意内容生产 | A(角色) + A(Few-shot 风格) + E(Critique-Revise) | 定人设、克隆文风、分离批评与生成 |
| Agent 工作流 | D(ReAct) + C(工具 schema) + E(反思) | 工具调用硬约束 + 失败后反思重试 |
| 跨模型迁移 | F(版本化) + 03-benchmark 对照实验 | 同一任务多模型跑，产出 per-model variant |
