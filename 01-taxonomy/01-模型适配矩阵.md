# 模型适配矩阵

> **一律按"族"划分，不锁死版本号。** 型号、价格、上下文长度迭代极快，引用前以各厂商官方文档为准。
> 本文件的价值在于**划分逻辑**，版本填进去即可用。

## 一、先纠正三个常见误解

在列矩阵之前，这三条比"哪个模型配哪个技术"更重要。

**1. 模型已分化为"指令遵循型"与"自主推理型"，提示词策略根本不同。**
带显式推理档位的模型内部已有训练好的推理轨迹。对这类模型手写 CoT 是冗余甚至有害的——会与内置轨迹冲突，表现为过度冗长或提前收敛。正确用法是**调档位参数 + 给判定标准**。

**2. 结构化输出应走 API 原生 schema，而不是靠 prompt 恳求。**
Prompt 只能提高概率，constrained decoding 是硬保证。生产环境里还在用"请务必输出合法 JSON"的，是没用对工具。

**3. Few-shot 的收益点已迁移。**
现在 Few-shot 买的是**格式与风格**，不是能力。强模型 zero-shot 就能分类，但对特定表格结构、键名、文风的对齐，3 个例子依然最快最稳。

## 三、跨模型差异的三个层次

> **重要澄清**：网上常说"四大模型族各有方言，提示词不能通用"——这个说法**被夸大**了。
> 真实情况是分三层的，绝大多数场景落在第一层，那里根本不存在方言问题。

### 第一层：通用层（约八成，无差异）

指令明确、给上下文、给示例、指定输出格式、拆分复杂任务——这些原则在所有模型上通吃。

**GPT 风格的提示词写法是事实上的通用语。** 一份写得好的 prompt 直接换到 Claude / Gemini / Qwen 上，绝大多数情况下能正常工作。这一层不需要为不同模型准备不同版本。

### 第二层：格式偏好层（约一成半，是"优化"不是"必须"）

各厂商官方文档确实推荐了不同写法，但**这只是偏好，不是硬性要求**：

| 模型族 | 官方推荐写法 | 实际影响 |
|---|---|---|
| **Claude 系** | `<XML 标签>` 分区 | XML 在超长 system prompt 下分隔效果略好；用 Markdown 也完全可用 |
| **GPT 系** | Markdown 分节 + 编号步骤 | 与模型对齐度最高；编号步骤对多步任务有小幅帮助 |
| **Gemini 系** | 指令宜短，原文整块塞入 | 长上下文下"少指令多素材"更符合其设计 |
| **国产开源系** | 中文结构化分条 | 对 system 角色敏感度偏低，**关键约束建议在末尾重申** |
| **图像生成系** | 主体 + 风格 + 参数 + 负向提示词 | **真·独立体系**，与 LLM 提示词几乎不通用 |

判断标准：这一层值得优化，但**优先级低于把指令本身写清楚**。用 Markdown 写 Claude 的 prompt 不会让结果崩掉。而且随着模型能力增强，这一层的差距在持续收敛。

### 第三层：系统配置层（占比小，但权重最大）

这才是真正影响结果的差异，而且它**不是提示词写法问题**：

| 维度 | 为什么影响大 |
|---|---|
| 推理档位参数 | reasoning effort / extended thinking / thinking budget——决定计算资源分配，影响远大于任何措辞技巧 |
| 原生 structured outputs | 有没有、成熟度如何，直接决定结构化输出是硬保证还是软概率 |
| 上下文窗口量级 | 10⁵ 与 10⁶ 之差，决定任务是"整库喂入"还是"必须分块检索"，是架构级差异 |
| 多模态支持 | 能不能吃图/视频，决定整个方案能不能成立 |

**结论**：与其纠结 XML 还是 Markdown，不如把时间花在"选对模型族 + 配对档位参数 + 用对原生 schema"上。

### 长上下文通用规则（适用于所有族）

- 指令置于**末尾**，而非开头——模型对尾部内容注意力更强
- 关键约束**重复两次**（开头一次、末尾一次）
- 用显式分区（XML 标签 / Markdown 标题）降低检索难度
- needle-in-a-haystack 跑分全绿 ≠ multi-needle 跨段推理可用，需实测

> ⚠️ **未实测声明**：本节"三层占比"是基于工程体感的定性分层，**没有实测数据支撑**。
> 跨模型表现差异的具体幅度，必须靠 `03-benchmark/` 的对照实验自己测出来，不要引用任何二手数字（包括本文早期的估计值）。

## 四、技术 × 模型适配矩阵

| 技术类 | 首选模型族 | 关键理由 | 常见反模式 |
|---|---|---|---|
| **A 语境注入** | 全族通用；格式对齐优先 GPT / Claude | Few-shot 主要买格式，弱模型收益更大 | 在推理型模型上堆 20 个例子 |
| **B 推理激发** | 推理档模型：GPT 系 reasoning、Claude extended thinking、DeepSeek-R1、Qwen3 / GLM thinking | 手写 CoT 只对**非推理档**有效 | 对已开 thinking 的模型再写"逐步思考" |
| **C 结构约束** | GPT（structured outputs）、Gemini（constrained decoding）、Claude（tool-use schema） | 原生 schema 是硬保证 | 用自然语言描述 JSON 格式 |
| **D 流程编排** | GPT（工具生态）、Claude（长程 agent 稳定）、Kimi K2（开源 agentic 强） | 看长任务的上下文保持能力 | 单条 prompt 塞十个步骤 |
| **E 反馈迭代** | Claude（批判性最强）、GPT 高推理档 | 需先给可判定的评分标准 | 无判据的"请再优化一下" |
| **F 元层自动化** | **强模型生成 → 弱模型执行 → 独立判据评分** | 同模型自评自改会放大偏见 | 让同一模型既写又评 |
| **长上下文** | Gemini、Kimi K2、MiniMax | 指令置末尾 + 关键约束重复 | 指令堆开头后接十万字 |
| **多模态** | Gemini（视频最强）、GPT、Qwen3-VL | 图像/视频/文档混合输入 | 拿纯文本模型处理图表 |
| **图像生成** | Midjourney、Flux、SDXL、Imagen | 负向提示词独立体系 | 把 LLM 提示词写法套到扩散模型 |
| **中文创作** | Qwen3、豆包、GLM、DeepSeek | 语感、公文体、本土化表达 | 用海外模型写中文公文 |
| **合规 / 数据主权** | Qwen3、DeepSeek、GLM、Llama、Mistral | 可自部署，数据不出境 | 敏感数据走境外 API |
| **成本敏感** | Gemini Flash、DeepSeek、GLM、豆包 | 分档路由，简单任务不上旗舰 | 全量任务跑旗舰模型 |

## 五、选型决策顺序

按顺序问，不要跳步：

1. **数据能否出境？** 不能 → 国产开源系 / 国际开源系，自部署
2. **是否中文创作 / 本土化表达为主？** 是 → 国产系
3. **是否需要机器解析的结构化输出？** 是 → 优先选有原生 schema 支持的族
4. **任务是否需要长推理链？** 是 → 选有推理档位的模型，**调档位而不是手写 CoT**
5. **成本 / 延迟约束？** 严格 → 分档路由：简单任务走 Flash / mini 级，复杂任务才上旗舰

## 六、反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 以为提示词必须逐模型重写 | 把 80% 通用的部分重复劳动，且难维护 | 一份通用底稿 + 仅在第三层（档位/schema/上下文）做 per-model 适配 |
| 以为一份 prompt 能无脑打天下 | 忽略了档位参数与 schema 支持等架构级差异 | 至少在选型时走一遍第五节决策顺序 |
| 用 prompt 恳求 JSON 格式 | 偶发非法输出 | 走 API 原生 schema |
| 对推理型模型手写 CoT | 冗长、提前收敛 | 调 reasoning effort / thinking 档位 |
| 例子越多越好 | 挤占上下文、边际收益为负 | 3–5 个高质量、分布匹配的例子 |
| 否定句堆叠约束 | 部分模型反而激活被禁项 | 改写为正面指令；约束 >7 条时分层 |
| 无判据的自我迭代 | 随机游走，质量不升 | 先定义评分标准再迭代 |
| 全量任务上旗舰 | 成本失控 | 按任务难度分档路由 |
