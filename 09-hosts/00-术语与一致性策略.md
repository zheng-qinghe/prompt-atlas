# 术语与一致性策略

---

## 一、术语：Agent 宿主（Agent Host）

### 用法

本项目统一用 **Agent 宿主（Agent Host）** 指代各类能够加载并执行提示词预设、技能包、专家配置的 AI 应用平台。不使用具体厂商或产品名。

### 定义出处

该术语源自 **MCP（Model Context Protocol）官方架构规范**，是其中的正式概念。规范原文对三层架构的定义：

| 概念 | 官方定义 |
|---|---|
| **Host（宿主）** | AI 应用本身。管理会话状态，决定连接哪些 Server，控制用户授权边界 |
| **Client（客户端）** | 宿主内部的协议通信处理器，与单个 Server 保持一对一连接 |
| **Server（服务器）** | 暴露能力（工具、资源、提示词模板）的轻量级进程 |

MCP 规范对 Host 职责的完整描述：创建并管理多个 client 实例、控制连接权限与生命周期、执行安全策略与同意机制、处理用户授权决策、协调 AI/LLM 集成与采样、跨 client 聚合上下文。

### 为什么用这个词

1. **中立**：不绑定任何厂商，资产定义不会因某平台改版而失效
2. **有出处**：是公开标准里的正式术语，不是自造词，可被查验
3. **语义准确**：准确描述了这类平台的本质——承载模型、管理会话与授权边界的"宿主"，而我们在其上加载的提示词与技能，是寄宿于其中的能力扩展

### 不使用的词

- ❌ **Harness**：Anthropic 内部语境中确有此用法（指驱动模型的宿主系统），但与某同名商用 CI/CD 产品冲突，易混淆
- ❌ **平台 / 工具 / 客户端**：过于宽泛，无法与"普通软件"区分

## 二、宿主类型（按能力形态分类）

不按厂商分，按**能力形态**分。同一类型内的宿主，资产部署方式基本一致。

| 类型 | 形态特征 | 典型加载方式 |
|---|---|---|
| **A 通用助手型** | 对话式，支持技能包 + 专家/人格配置，多支持标准工具协议 | 技能目录 + 配置文件 |
| **B IDE 内嵌型** | 集成在编辑器中，面向编码，多支持项目级规则文件 | 项目级规则 / 配置文件 |
| **C 终端 CLI 型** | 命令行环境，纯文本交互，配置以文件为中心 | 配置文件 + 命令注册 |
| **D 流水线型** | 集成在自动化流程中，无交互，靠配置驱动 | 流水线配置 + 脚本 |

> ⚠️ 具体哪些产品属于哪一型、各自的配置文件路径与格式，**需逐个实测后填入**，不凭印象填写。

## 三、宿主能力维度对照

判断一个宿主能承载多复杂的资产，看这六个维度。

| 维度 | 说明 | 缺失时的降级方式 |
|---|---|---|
| 提示词预设加载 | 能否注册可复用的提示词模板 | 手工复制粘贴 |
| 技能包机制 | 是否有 Skill / 命令 / 插件式的可加载单元 | 降级为提示词预设 |
| 专家 / 人格配置 | 能否定义角色、专家团并持久生效 | 降级为 system prompt 文本 |
| 工具扩展协议 | 是否支持 MCP 等标准协议 | 降级为工具能力文字描述 |
| 项目级配置 | 是否有项目级配置文件（随仓库走） | 降级为全局配置或手工注入 |
| 上下文注入方式 | 自动加载 vs 需手动调用 | 影响触发设计，需写明调用方式 |

**降级链**（从富到贫）：
```
技能包 → 提示词预设 → system prompt 文本 → 手工复制
```

设计资产时按**最贫宿主**保底，按**最富宿主**增强——这样资产在任何宿主上都至少有可用形态。

## 四、一致性策略：源格式 + 适配器

### 问题

同一套能力（比如一个"代码审查"技能）在四类宿主上的文件格式、加载方式、触发机制各不相同。逐个手写一遍的结果是：改一处要改四遍，且必然漂移。

### 方案

维护**一份中立源格式**，用**适配器**转换为各宿主格式。

```
    源格式（本项目维护，宿主中立）
              │
    ┌─────────┼─────────┬─────────┐
    ▼         ▼         ▼         ▼
  适配器A   适配器B   适配器C   适配器D
    │         │         │         │
    ▼         ▼         ▼         ▼
  类型A宿主  类型B宿主  类型C宿主  类型D宿主
```

改内容只改源格式，重新跑适配器即可全平台同步。这是 L4 层的核心价值。

## 五、源格式定义

一个技能包的源描述应包含以下字段。**这是本项目要标准化的关键交付物。**

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 全局唯一标识 |
| `name` | ✅ | 人类可读名称 |
| `version` | ✅ | 语义化版本号 |
| `description` | ✅ | **何时该触发本技能**——决定能否被正确调用，最关键字段之一 |
| `trigger` | ✅ | 触发条件：关键词 / 文件类型 / 显式调用 |
| `instructions` | ✅ | 核心指令正文 |
| `constraints` | ⬜ | 硬性约束（禁止项、边界、失败行为） |
| `output_format` | ⬜ | 输出契约（schema / 模板 / 格式要求） |
| `resources` | ⬜ | 依赖文件清单 |
| `tools` | ⬜ | 所需工具能力（宿主不具备时按降级链处理） |
| `model_hints` | ⬜ | 模型适配提示（档位建议、是否需要原生 schema） |
| `meta` | ⬜ | 作者、许可证、变更记录 |

### 为什么每个字段必要

- `description` 与 `trigger` 决定"能不能被正确触发"——技能包最常见的失败不是写不好，而是**根本没被唤起**
- `constraints` 与 `output_format` 对应六类中的 C 结构约束，是输出可控的前提
- `tools` + 降级链，决定资产能否在低能力宿主上保底可用
- `model_hints` 承载第三层（系统配置层）的适配信息，与 `01-taxonomy/01-模型适配矩阵.md` 衔接

## 六、适配检查清单

把一份资产部署到新宿主时，逐项确认：

- [ ] 该宿主属于哪一型？配置文件路径与格式是什么？
- [ ] 是否支持技能包机制？不支持则降级到哪一级？
- [ ] 触发机制如何工作？`description` 是否需要按宿主习惯重写？
- [ ] 依赖的工具能力是否具备？不具备时降级方案是否可行？
- [ ] 输出契约能否被宿主保障？不能则需改为提示词软约束 + 后置校验
- [ ] 是否需要针对该宿主的推理档位 / schema 支持做参数调整？
- [ ] 部署后是否跑过一次冒烟测试（触发 → 执行 → 输出符合契约）？
